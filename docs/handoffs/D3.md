## Implemented

- k6 E07 write, E08 paginated read, E08 radius read and documented mixed workload;
- environment-driven base URL, credentials, VUs, duration, seed and query settings;
- JWT lifetime check covering warm-up, steady run and ramp-down;
- deterministic seed generator through E07, with a 70% dense / 30% wide location mix;
- explicit reset guard for a separately named benchmark Compose project/database;
- per-repetition raw k6, summary, seed manifest and optional Docker stats paths;
- Kaggle CPU notebook that distinguishes generator-only from server-on-Kaggle and
  reports missing Java/k6/Docker/server capability instead of assuming success.

The 50-VU run had one iteration interrupted during ramp-down but zero failed HTTP
requests and zero failed checks; it is retained as observed evidence, not hidden.
The 100-VU raw artifact is large because every sample is intentionally preserved.

Docker stats were sampled during the load ladder. Backend average/max CPU was
approximately 208.68%/790.33% at 10 VU, 306.05%/451.29% at 50 VU and
238.21%/494.43% at 100 VU; database average/max CPU was 69.92%/212.42%,
142.44%/324.68% and 194.88%/333.07%, respectively. Backend memory peaked at
7.56%, 8.87% and 9.22%; database memory peaked at 2.14%, 2.14% and 2.15%.
These Docker percentages are container samples on this host, not portable capacity
limits.

The run directories are `benchmark/results/20261024-142105-01` through
`benchmark/results/20261024-142703-01`; they are ignored by Git and contain the
raw/summary/configuration evidence. The repository does not claim Kaggle complete:
the notebook preflight found Python 3.14, Java 21 and Docker locally, but native k6
and a configured Kaggle server were absent.

The measured topology was a Windows host (Acer Nitro AN515-58, Intel i5-12500H,
16 logical processors, 15.7 GiB RAM), Docker Desktop engine 27.3.1, Compose project
`gdrn-benchmark`, backend plus PostGIS database, and a `grafana/k6` container using
`host.docker.internal`. Images were `grafana/k6@sha256:e66db15b...` and
`postgis/postgis@sha256:94146ac3...`; the backend was built from the branch commit.
This is enough to reproduce the topology, not a portable capacity specification.

When running, attach the complete timestamped result directory rather than copying
only percentile numbers. Include `raw.json`, `summary.json`, `run.json`, `seed.json`
when used, and `docker-stats.csv` when the collector had Docker access.

## Known limitations

- Native k6 was not assumed to be installed; the runner supports a local
  `grafana/k6` Docker image. Kaggle may not have a Docker daemon.
- CPU/RAM is sampled only when Docker container names and the Docker daemon are
  available; otherwise the report must say unavailable.
- No public DB/service/tunnel is created by the notebook or scripts.
- A benchmark credential is required, but credentials are never written to the
  notebook, manifests or Git.
- The read workloads require the generator to populate the disposable database
  before each repetition; write-only runs should start after reset.
- The k6 summary exporter includes setup data by default; the repository runner
  removes its JWT before saving `summary.json`, while raw samples are checked for
  credential fields.
